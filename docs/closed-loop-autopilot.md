# Recommend-only Closed-Loop Autopilot

v1.0 composes the earlier subsystems into one auditable decision layer.

The autopilot does **not** apply Kubernetes manifests, submit Slurm jobs, evict workloads, migrate jobs, or otherwise mutate scheduler state.

## Inputs

A decision starts with:

- a saved baseline optimization
- a saved candidate optimization
- scheduler backend
- available GPU count
- workload command
- guarded-validation thresholds

It can additionally consume:

- a statistical study
- a telemetry correlation report
- a per-GPU time-series report
- deployment-policy limits such as maximum GPUs or exact GPU count
- node selectors

## Decision states

### Promote

A candidate is marked `promote` when:

- guarded validation accepts it
- the deployment policy accepts both plans
- the candidate plan differs from the baseline unless equivalent plans are explicitly allowed
- every required evidence source is present
- configured statistical evidence gates pass
- configured telemetry/time-series risk gates pass

Promote means **recommended for operator-controlled rollout**. It does not execute the rollout.

### Hold

A candidate is marked `hold` when explicit validation passes but confidence or operational evidence is insufficient.

Typical hold reasons include:

- required study/correlation/time-series evidence is missing
- study does not contain the candidate run
- too few replicates
- config-selection stability below threshold
- candidate is not on the required Pareto frontier
- correlation references a different optimization
- high mean memory pressure
- high peak temperature
- per-GPU utilization stragglers
- per-GPU memory/temperature threshold violations
- no meaningful deployment-plan change

Hold is deliberately distinct from reject. It means the candidate is not proven safe enough to recommend yet.

### Reject

A candidate is marked `reject` only when the guarded-validation layer fails an explicit policy threshold, such as:

- insufficient throughput gain
- excessive p99-latency regression
- excessive energy regression
- excessive memory-pressure regression
- failed benchmark exit status
- missing metric required by a configured guardrail

## Rollback plan

Every decision includes a rollback record, even for a promote decision.

The rollback record stores:

- baseline configuration label
- complete baseline deployment-plan snapshot
- trigger reasons
- operator steps

The steps intentionally require an external operator-controlled workflow to perform any scheduler mutation.

## Scheduler safety

The autopilot engine refuses a deployment policy with `recommend_only=False`.

The CLI always constructs a recommend-only deployment policy.

This is a hard v1.0 boundary.

## Statistical evidence

When a study is supplied, the autopilot locates the group containing the candidate optimization and can enforce:

- minimum replicate count
- minimum dominant-config stability
- candidate membership on the study Pareto frontier

These gates operate on the statistical evidence generated by v0.9 rather than recomputing study statistics.

## Telemetry evidence

When a correlation report is supplied, the autopilot can hold on:

- mismatched candidate optimization
- high mean memory pressure
- high peak temperature

When a per-GPU time-series report is supplied, it can hold on:

- persistent utilization stragglers
- per-GPU high memory pressure
- per-GPU high temperature

The telemetry gates are conservative evidence checks, not root-cause claims.

## CLI

```bash
agoctl autopilot decide \
  --baseline-optimization baseline-run \
  --candidate-optimization candidate-run \
  --backend kubernetes \
  --available-gpus 8 \
  --max-gpus 8 \
  --min-throughput-gain 5 \
  --max-p99-regression 5 \
  --study study-id \
  --require-study \
  --correlation correlation-id \
  --require-correlation \
  --timeseries timeseries-id \
  --require-timeseries \
  --node-selector accelerator=h100 \
  -- python serve.py
```

Persisted reports live under:

```text
.ago/autopilot/
```

Inspect them with:

```bash
agoctl autopilot list
agoctl autopilot show <decision-id>
```

## Exit codes

- `0`: promote
- `4`: hold
- `3`: reject
- `2`: invalid input, missing artifact, or policy/planning error

## Future mutation boundary

A future mutating controller should not simply remove the recommend-only flag.

Before automatic rollout is considered, the project should add:

- scheduler-native transaction/ownership semantics
- deployment health checks
- canary traffic or workload isolation
- automatic rollback execution with verification
- durable event/audit logs
- concurrency control and leader election
- crash-safe state transitions
- multi-node Kubernetes primitives such as JobSet/Kueue where appropriate
- security review for cluster credentials and permissions
